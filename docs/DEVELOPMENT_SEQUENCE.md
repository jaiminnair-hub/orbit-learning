# Development Sequence — Phase 1

This is the granular build order for Phase 1 only (Platform foundation). It replaces the coarser "Phase 1" line item from the Stage 1 roadmap with an explicit step order, since — per the brief — **nothing else depends on the system until this foundation passes its tests.**

## Progress (updated 2026-08-14)

All 11 steps done and verified — not just marked complete. **Phase 1 is functionally complete**; see [DEFINITION_OF_DONE.md](DEFINITION_OF_DONE.md)'s step 11 verdict for the three deliberately-deferred items (none block Phase 2) and the recommendation to proceed.

7. ✅ **Supabase Auth wiring** — signup, login, password reset, logout, session handling via `getSessionContext()` called from the `app/(app)` route-group layout ([API_SPEC.md](API_SPEC.md) §1 — not `middleware.ts`). Proven end to end against **both** `next dev` and the real Workers preview (`workerd`): signup → session cookie → protected route → survives reload → logout → password-reset email (fetched from Mailpit, real link followed) → callback route → new password → login with it. This also closed out the two previously-untested Cloudflare validation items (Supabase Auth, server/client access) — see [CLOUDFLARE_VALIDATION_RESULTS.md](CLOUDFLARE_VALIDATION_RESULTS.md). One real bug found and fixed along the way: `supabase/config.toml`'s default redirect-URL allowlist was wrong (wrong protocol/host), silently dropping custom `redirectTo` values — caught only by following the actual email link, not by checking that the request didn't error.
8. ✅ **RBAC enforcement** — `lib/api/with-auth.ts` wraps API route handlers with session resolution (via `getSessionContext()`, the same function the route-group layouts use) and an optional `minRole` gate, checked against `lib/auth/roles.ts`'s `hasRole()` — a TypeScript mirror of the DB's `role_rank()` so the API-layer check and the RLS check underneath agree on the same hierarchy. Three real routes prove it: `GET /api/v1/orgs/me` (any authenticated user), `GET /api/v1/orgs/members` (`minRole: "manager"`), and `GET /api/v1/platform-admin/orgs` (`is_platform_admin()`-gated, not part of the tenant role hierarchy — see [MULTI_TENANCY.md](MULTI_TENANCY.md) §4). All three verified against the real remote Supabase project and a real running `next dev` server: signed in as a genuine `learner`, `manager`, and platform-admin test user (via real cookie-based sessions in a real browser, not curl with a bearer token — this stack's server client only reads cookies), confirmed the exact status/body for every case (200/200/403 for manager, 200/403/403 for learner, and a genuine cross-tenant 200 for the platform admin against an org they had zero membership in). The platform-admin route also closes the last open item in [MULTI_TENANCY.md](MULTI_TENANCY.md) §4: every cross-tenant read writes an `activity_log` row via a new service-role client (`lib/supabase/admin.ts`) — verified for real by querying `activity_log` after the requests and finding both rows, correct `actor_id` and `count`. Test data (2 orgs, 3 users, 2 log rows) was created and cleaned up via the Supabase Admin API, not left in the real project. `SUPABASE_SECRET_KEY` (previously blank) is now populated in `.env.local` — needed because `activity_log` deliberately has no insert policy for `authenticated` (service-role only, by design, see [MULTI_TENANCY.md](MULTI_TENANCY.md) §2a).
9. ✅ **Minimal admin UI** — create an org, invite a user, accept the invite, assign a role. Deliberately thin (plain inline-styled forms, no design system yet), and every mutation goes through the step-8 API layer via `fetch()` rather than a Server Action or direct Supabase call, per this step's own "exercise UI → API → RLS end to end" intent. Four new routes back it: `POST /api/v1/orgs` (create org, caller becomes `org_owner` — organizations has no RLS insert policy by design, and `profiles.role`/`org_id` can only change via `service_role` per the escalation-prevention trigger, so this and every other mutation below use `lib/supabase/admin.ts`), `GET`/`POST /api/v1/orgs/invitations` (`minRole: org_admin`; uses the caller's own session client, not service-role, since RLS already permits org_admin+ read/write on `org_invitations`), `POST /api/v1/orgs/invitations/accept` (token lookup + profile assignment, email-match guard, single-use via the "already in an org" check), and `PATCH /api/v1/orgs/members/[id]` (role assignment — the first dynamic-params route in the app; `withAuth()` was generalized to forward Next 16's `{ params: Promise<...> }` route context, verified against `node_modules/next/dist/docs` rather than assumed). New pages: `app/(app)/dashboard` (create-org form when org-less), `app/(app)/admin` (org_admin+ gate, invite form, pending invitations with a copyable accept link — no email delivery is wired up yet, so the link is the whole mechanism for now, shared out of band), `app/(app)/invite/[token]` (accept flow). Verified for real, not just typechecked: two fresh confirmed test users signed in through the actual browser UI — one created an org through the real form, invited the other as `manager` through the real admin console, the second followed the real accept link and landed in the same org with the invited role. Also verified the guard rails for real: a `manager` blocked from `/admin` and from the invite/create-org APIs (403/409), re-accepting an already-used invite blocked (409), an `org_admin` blocked from inviting/granting a role above their own rank (403) and from changing their own role via the route (403), and after promotion to `org_admin` the same user could invite at their own rank successfully (201) and reach `/admin`. Test data created and cleaned up via the Supabase Admin API.
10. ✅ **Full authentication/authorization/tenant-isolation test suite green against the running app** (not just the data layer in isolation) — API-level and Playwright-level tests from [TESTING.md](TESTING.md) §2–4, §6. Built in two passes, both landed:

    **Pass 1 — Playwright golden path.** Added `@playwright/test`, `playwright.config.ts`, `tests/e2e/onboarding.spec.ts`. The config's `webServer` spawns `next dev` with env vars pointed at the *local, disposable* Supabase instance (read via `supabase status -o json`, mirroring `tests/setup/local-supabase.ts`'s approach) rather than the real project `.env.local` points to — shell env vars override `.env.local` in Next's precedence order, so no `.env` file needed to change. `npm run test:e2e` is self-sufficient (`supabase start && playwright test`), and CI installs the Chromium browser and runs it as a step after `npm test` (same job, same already-running local Supabase instance). The spec drives the real rendered UI end to end: sign up → create org → invite a second user (`manager`) → log out → sign up as the invitee → accept the invite via the real link → verify the assigned role → log out → log back in with real credentials → verify the session persists.

    Two real things pass 1 surfaced, not just flakiness to paper over: a real bug in `app/(app)/invite/[token]/accept-invite.tsx` (the "Go to dashboard" button used `router.push("/dashboard")` alone, which can serve a **stale cached** `/dashboard` render from before the invite was accepted, still showing "no org yet" — Next's client router cache, not a data problem; fixed by also calling `router.refresh()`), and Playwright's default 5s per-assertion timeout being genuinely too tight for this stack in dev mode (Turbopack cold-compiles each route on first hit, real round trips go to a Dockerized Postgres/GoTrue stack — a `POST /signup` was observed taking 2–3s end to end even though it succeeded, confirmed via `docker logs supabase_auth_LMS`, `status:200`; raised to `expect: { timeout: 15_000 }`, overall test timeout to 90s). Reran 3 consecutive times with zero failures before calling it stable.

    Deliberately scoped narrower first — the Playwright/CI/local-Supabase-dev-server plumbing is a one-time shared cost across every spec file, so validating it against one known-working flow first was cheaper than debugging it under three specs at once. Discussed with the user before starting.

    **Pass 2 — API-level role-matrix and tenant-isolation automation.** Added `tests/e2e/global-setup.ts` (runs once per Playwright invocation): seeds one org with `learner`/`manager`/`org_admin`/`org_owner`/a dedicated `patchTarget` user via the service-role client (this pass tests API authorization, not the onboarding mechanism again — mirrors `tests/setup/seed.ts`'s "simulate invited and accepted" pattern from the Vitest suite), a second unrelated org with its own owner (for tenant isolation), and a platform admin — then logs each in for real through the actual `/login` form (Supabase's `@supabase/ssr` cookie format is internal, not worth reverse-engineering) and persists each session via Playwright's `storageState` for reuse across specs.

    `tests/e2e/role-matrix.spec.ts` (5 tests): every role against `GET /api/v1/orgs/me`, `GET /api/v1/orgs/members`, `POST /api/v1/orgs/invitations` (including the "can't invite above your own rank" guard), `PATCH /api/v1/orgs/members/[id]` (self-role guard, above-rank guard, and a real successful within-rank grant verified by re-reading the response body), and `GET /api/v1/platform-admin/orgs`. `tests/e2e/tenant-isolation-api.spec.ts` (5 tests): `/orgs/me` and `/orgs/members` never leak cross-org data, an `org_admin` PATCHing a different org's member 404s, an invitation can only be accepted by the email it was sent to (`EMAIL_MISMATCH`), and a platform admin's cross-tenant read is genuinely cross-tenant (both seeded orgs appear) while a normal `org_owner` gets 403 on the same route. All 11 Playwright tests (this pass's 10 plus pass 1's 1) run serially (`workers: 1` — specs share seeded state, and role-matrix's `PATCH` tests mutate it) and passed on the first real run; reran 3 consecutive times with zero failures, alongside the existing 12-test Vitest suite, before calling it done.
