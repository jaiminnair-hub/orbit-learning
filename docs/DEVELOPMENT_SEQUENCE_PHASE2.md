# Development Sequence — Phase 2

The granular build order for Phase 2 (Content + Core LMS — content library, courses, SCORM, enrollment, per [ROADMAP.md](ROADMAP.md)), in the same spirit as [DEVELOPMENT_SEQUENCE.md](DEVELOPMENT_SEQUENCE.md) did for Phase 1: small, dependency-ordered steps, each verified against real infrastructure before the next one starts, gated by a Definition of Done before Phase 3 begins.

## Why this phase is sequenced differently than Phase 1

Phase 1 had an earlier project's org/RBAC model to read as a reference while building something better. Phase 2 doesn't — there is no an earlier project CMS to extract from; the whole reason this is rated the highest-complexity item in the original Stage 1 audit is that it's genuinely new. Two consequences for the order below:

1. **The two real unknowns get de-risked early (steps 2 and 3), not left until the end.** A real SCORM package on Cloudflare Workers and the content-versioning mechanic ("a learner mid-course doesn't see content shift under them") are both things this stack has never actually proven — [CLOUDFLARE_VALIDATION_RESULTS.md](CLOUDFLARE_VALIDATION_RESULTS.md) only got a *partial pass* on SCORM, and versioning has only ever been designed on paper ([CONTENT_MODEL.md](CONTENT_MODEL.md) §5). If either forces an architecture change, finding that out in step 2–3 is cheap; finding it out after the full CMS is built on top of it is not.
2. **Tenancy discipline from Phase 1 carries forward without exception.** Every table below gets `org_id` + the standard four-policy RLS shape in the same migration that creates it — this is the one lesson from the original an earlier project audit this whole platform exists to not repeat, and Phase 1 proved the pattern works. No table in this phase is exempt.

## Progress (updated 2026-08-16)

**All 9 steps done and verified.** Phase 2 is functionally complete — see [DEFINITION_OF_DONE_PHASE2.md](DEFINITION_OF_DONE_PHASE2.md) for the box-by-box review against real evidence, including what is deliberately deferred and why. Phase 3 (Assessment + Certification) is next.

Both unknowns this phase was sequenced around held up: SCORM works on the real `workerd` runtime, and the versioning mechanic protects an in-progress learner from later republishes. Neither forced a design change.

## Sequence

1. ✅ **Content asset foundation** — `content_assets` table ([DATABASE.md](DATABASE.md) §3: `type`, `storage_path`, `mime_type`, `file_size`, `checksum`, `status`, `version`), RLS + `org_id` from the first migration (`supabase/migrations/20260815100000_content_assets.sql`), applied to both the local disposable instance and the real remote project. The private `content-assets` Storage bucket is created in the same migration, so local and remote can't drift.

    Two routes implement the two-step signed-upload flow from [API_SPEC.md](API_SPEC.md) §6: `POST /api/v1/content/upload-url` (`minRole: org_admin`, returns a signed upload URL scoped to an `org_id/...` path prefix per [MULTI_TENANCY.md](MULTI_TENANCY.md) §5) and `GET`/`POST /api/v1/content/assets` (confirms the object actually landed in Storage before creating the row). The bucket is private with no `storage.objects` RLS policy on purpose — every upload and download is mediated server-side through the service-role client, so there is no direct client path to the bucket at all.

    **Verified against real infrastructure, not just typechecked**, on **both** the local instance and the real remote project: signed URL issued → a real file `PUT` to Storage (200) → confirmed and row created (201) → the file re-downloaded and its bytes, size, and MIME type checked. Three guard rails were each proven by actually attempting them: registering an asset under *another org's* storage prefix (400), registering one for a file that was never uploaded (404 — the route verifies against Storage rather than trusting the client), and an invalid content type (400). This closes the "Supabase Storage/signed URLs against the real project" item Phase 1's [DEFINITION_OF_DONE.md](DEFINITION_OF_DONE.md) deliberately deferred — closed organically by the feature that needed it, exactly as that review recommended, rather than validated speculatively.

    Both test suites were extended in the same step rather than later: `tests/tenant-isolation.test.ts` gains the `content_assets` rows (cross-org read denied, cross-org insert denied), `tests/e2e/role-matrix.spec.ts` gains the content routes' `org_admin` gate (including asserting the signed path is namespaced to the caller's own org), and `tests/e2e/tenant-isolation-api.spec.ts` gains the API-layer isolation case. 14 Vitest + 13 Playwright tests green, each suite run 3 consecutive times.

    Two real environment findings, both fixed here rather than left to surprise someone later: Supabase Storage had been disabled in `supabase/config.toml` since Phase 1 and its container fails the CLI's health probe on this machine even though the service itself starts correctly (`npm test`/`npm run test:e2e` now pass `--ignore-health-check`, and the service is verified reachable separately); and enabling Storage pushed `npx supabase status` to ~7–8s, which every Vitest file pays once — that alone consumed most of the old 15s `testTimeout` and made `schema-hygiene` time out on a query that isn't slow, so the timeout was raised to 45s with the reason recorded in `vitest.config.mts`.
2. ✅ **SCORM spike — de-risked before anything is built on top of it.** A real SCORM 1.2/2004 package uploaded, extracted server-side, served with the correct `Content-Type` via a signed URL, and a real CMI progress round-trip proven against the live Cloudflare Workers runtime, not just `next dev`. `scorm_packages`/`scorm_progress` tables (reusing an earlier project's table shape, tied in via `scorm_packages.content_asset_id`). This closes Phase 1 DoD's other deferred SCORM item and is sequenced here specifically because a failure here is the one thing in this phase that could force a real design change — better to know in week one.
3. ✅ **Learning objects + the versioning/workflow mechanic — proven, not just designed.** `learning_objects`, `learning_object_assets` (composition join), `content_versions` (polymorphic snapshot), `content_reviews` (polymorphic audit trail). Before building any authoring UI: a real spike proving the actual scenario the design exists for — an org member enrolled mid-course keeps seeing the version they enrolled into while an author publishes a new version of a shared learning object underneath them. If the snapshot/publish mechanic doesn't hold up under a real test here, it's a schema question, not a UI bug to chase later.
4. ✅ **Course structure — lessons, modules, courses, and the actual reuse test.** `lessons`, `lesson_learning_objects` (the many-to-many reuse join — the entire point of separating content from structure per [CONTENT_MODEL.md](CONTENT_MODEL.md) §1), `modules`, `courses`. A minimal admin course-builder UI: create a course → add a module → add a lesson → attach learning objects. Proven for real by literally reusing one learning object in two different lessons and confirming an edit to it is reflected in both without duplication — the reuse mechanic gets exercised by an actual scenario, not just asserted.
5. ✅ **Course player — the learner-facing side.** Rebuilds an earlier project's `LmsModuleKit`/`ModulePlayer`/`LessonViewer` UI pattern (already identified as a clean, industry-agnostic extraction candidate) against the new schema. Wires in SCORM playback (step 2) and the non-SCORM content types (video/pdf/text/url/embed). A published course is playable end to end by a real learner account before enrollment/progress tracking exists — proves the player against static content first, so step 6's bugs are enrollment bugs, not player bugs.
6. ✅ **Enrollment & progress.** `enrollments` (polymorphic `enrollable_type`, unique per `(org_id, user_id, enrollable_type, enrollable_id)`), `progress` (per-learning-object, unique per `(org_id, user_id, learning_object_id)`). Admin/manager enrolls a learner; the learner's progress accumulates per learning object as they move through the player from step 5; course-level completion derives from it. Minimal learner/manager/admin dashboards (completion and pass-rate rollups only — no analytics beyond what's directly needed to see "who's done what").
7. ✅ **Real content search.** Generated `tsvector` columns on `content_assets`/`learning_objects`/`courses` ([CONTENT_MODEL.md](CONTENT_MODEL.md) §7), backing both the admin content-library search and the learner course search. This is the item [CLOUDFLARE_VALIDATION.md](CLOUDFLARE_VALIDATION.md)/tech-stack audit flagged in an earlier project as client-side `.includes()` over static arrays — Phase 2 is the first point real content exists to search, so it lands here rather than earlier as speculative infrastructure.
8. ✅ **Golden-path automation + full tenant-isolation extension.** A Playwright flow mirroring [TESTING.md](TESTING.md) §6 flow #2: admin creates a course (content library → learning object → lesson → module → course) → publishes it → a learner enrolls → completes it → (a SCORM-content variant of the same flow). `tests/tenant-isolation.test.ts` and `tests/e2e/tenant-isolation-api.spec.ts` gain the full "Read Org B's courses" row that [DEFINITION_OF_DONE.md](DEFINITION_OF_DONE.md) has carried as "doesn't apply yet" since Phase 1 — it applies now. `tests/e2e/role-matrix.spec.ts` gains the content-authoring matrix (who can create/edit/publish content vs. who can only view/enroll).
9. ✅ **Definition of Done review for Phase 2**, mirroring [DEFINITION_OF_DONE.md](DEFINITION_OF_DONE.md)'s Phase 1 review — a new `DEFINITION_OF_DONE_PHASE2.md`, reviewed box by box against real evidence, before Phase 3 (Assessment + Certification) begins.

## What's deliberately not in this phase

Held to exactly what [ROADMAP.md](ROADMAP.md) scopes for Phase 2 — content library, courses, SCORM, enrollment — and nothing past it:

- **Assessments, Question Bank, Certification** — Phase 3. `assessments`/`question_bank`/`certificates` exist in [DATABASE.md](DATABASE.md) §4 but no migration in this phase touches them.
- **Learning Paths and Programs** — course-bundling above the course level. Deferred until there's a concrete driver, per the roadmap's own phase discipline; `learning_paths`/`programs` tables wait.
- **AI Learning Assistant / Course Builder** — Phase 4, depends on this phase's content existing and being embeddable (`ai_knowledge_chunks`, [AI_ARCHITECTURE.md](AI_ARCHITECTURE.md) §4) — not built now, but step 3's `published`-only-content rule is exactly the gate that AI ingestion will later depend on.
- **Gamification, collaboration, ILT/virtual classroom scheduling** — no dedicated milestone; each folds into whichever later phase has a real reason to need it, per [ROADMAP.md](ROADMAP.md)'s reconciliation note.

## What explicitly does not start until step 9 passes

Phase 3 (Assessment + Certification) and everything after it. Same discipline as Phase 1: this sequence exists to prevent building assessments and AI features on a content model that hasn't been proven under real tenancy, versioning, and playback conditions.
