- **Full Critical→Low security-audit remediation, shipped and verified live (2026-09-16)** — a 5-domain audit (auth/tenant-isolation, AI/LLM, file-upload/export, injection/XSS/input-validation, secrets/HTTP-controls) surfaced findings from Critical to Low; every one was fixed the same day. Critical: a prototype-pollution gadget in the authoring JSON-Patch engine (`lib/authoring/json-patch.ts`) could walk into and pollute `Object.prototype` through the normal spec-edit endpoint via a `__proto__` pointer segment — closed with an explicit denylist. High: SCORM playback now fails closed instead of silently falling back to the insecure same-origin player when content isolation isn't configured in a *real* Vercel production deployment (gated on `NEXT_PUBLIC_VERCEL_ENV`, not `NODE_ENV` — this codebase's own e2e suite runs a production build locally/in CI on purpose, which a naive `NODE_ENV` check would have broken); a nonce-based Content-Security-Policy shipped (`proxy.ts`), closing a gap `next.config.ts` had deliberately deferred pending exactly this build-and-test pass. Medium: content-asset registration now cross-checks the declared type against what Storage actually recorded for the upload (closing an HTML/SVG-as-"image" stored-XSS surface), signed URLs for HTML/SVG force a download disposition, and invitation-accept now carries a rate limit like login/signup/reset. Low: the URL-import SSRF guard pins the DNS answer at fetch time rather than trusting a second lookup at connect time; embed iframes carry an explicit sandbox; HSTS adds `preload`; a new ESLint rule flags any `createAdminClient()` call with no adjacent justifying comment.

  **The CSP rollout surfaced and fixed a real regression of its own**: a statically prerendered page's HTML is generated once at build time, with no live request to draw a CSP nonce from — so Next's own hydration/RSC-payload `<script>` tags silently ran with no nonce at all, permanently mismatched against the fresh per-request nonce, and their JavaScript never executed. `app/orbit/complete` (the Orbit→Learning SSO bridge) hit this exactly: `verifyOtp()` never ran, the page never redirected, "Signing you in…" forever, with no console error a user would ever see — caught by a real e2e run, not code review, then root-caused by comparing dev-mode (works) against a production build (fails) and inspecting the actual served HTML for the missing nonce. Fixed the 4 affected pages with `force-dynamic` (splitting `app/orbit/complete/page.tsx` into a server wrapper + client component, since the route-config export only works from a Server Component) and added `scripts/check-no-static-pages.mjs` to the build itself, so any future page that silently goes static fails the build immediately instead of silently breaking in production.

  Also added `.github/workflows/weekly-security-audit.yml` — a scheduled, session-independent check (dependency vulnerabilities, lint, typecheck, an obvious-hardcoded-secret grep) that files a GitHub issue on failure, so this doesn't depend on anyone remembering to ask again.

  **Correction, 2026-09-11 — the "false alarm" above was wrong twice over.** The job-continuation call's real failure mode was neither the originally-suspected `SUPABASE_SECRET_KEY` mismatch nor, as later "corrected," a harmless artifact of local-script token signing. Reproduced live in production well after both of those verification runs: a full-course job would advance for a handful of steps, then go permanently silent — `status: running`, no error, no further progress. Vercel's own function logs showed the real cause: `[full-course-builder] unable to queue continuation ...: 508` — **HTTP 508, Loop Detected**, the platform's own guard against a deployment's functions calling each other in a cycle. The self-continuation design (each invocation making an authenticated HTTP call to its own `/advance-full` route to hand off to a fresh invocation) was exactly that cycle, and enough hops in a short window reliably tripped it — a real, code-level bug, not a false alarm, and not fixable by retrying the same pattern harder.
  **Fixed, same day**: the self-call is gone. `lib/ai/full-course-builder.ts`'s `advanceFullCourseJob` now simply stops when its invocation's time budget is spent, leaving the job `running` with its steps saved. Continuation is client-driven instead — `components/authoring/ai-generate-panel.tsx`'s poll loop (already polling every 2s for the progress label) calls `POST .../resume-full` once per tick whenever it sees no new step; a real browser tab calling an authenticated endpoint isn't a deployment calling itself, so the loop guard has nothing to trigger on. `resume-full` itself now runs synchronously (no more firing its work into a `next/server` `after()` block) and no longer resets `started_at` on every call, which would have made the one-hour job-age ceiling meaningless once it became the routine driver rather than a rare manual recovery action. ## Orbit ↔ Learning integration

### Scope 1 — LMS entry bridge: complete

The LMS verifies short-lived HMAC-signed Orbit entry tokens, rejects replay, requires a linked organisation and approved role map, and establishes the LMS session through Supabase. The bridge is POST-only; the token never enters the URL. This is not a database merge.

### Scope 2 — Orbit product-shell entry: complete

The Orbit authenticated shell checks entitlement and role server-side through `mint-lms-entry-token`, then hands an eligible user into Learning through a hidden form POST. Production verification covered valid entitlement/role, denied entitlement/no-role/expired-role states, a tampered organisation identifier, and a clean dashboard landing. ### Explicitly outside the completed scopes

No shared-data migration, shared identity provider, automatic learning-signal sync, unified reporting warehouse, or organisation/role-model consolidation has begun. OIDC/SAML is the intended long-term replacement for the temporary passwordless bridge.
